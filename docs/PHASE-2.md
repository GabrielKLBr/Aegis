# Phase 2 — CPU, exceptions, interruptions and guest clock

Date: 16/10/2026. Base: `D:\Desktop Folders (DO NOT ERASE)\AntiVirus`. **State: phase 2 completed. Phase 3 not initiated.**

## Behavior implemented

The `guardian-kernel-cpu.gk` image, version 0.2.0, runs in the WHP with a vCPU. The kernel installs TEM, RTD, TSS, break batteries and emergency STI. Sets up CR3, CR0.WP, EFER.SCE/NXE, STAR, LSTAR and FMASK within the guest. Confirms the tables installed with SGDT/SIDT/STR and the pagination root with CR3.

A self-test program runs in CPL3. The SYSCALL instruction enters the guest kernel, switches to a kernel stack and dispatches echo calls, clock query and execution termination. Unknown calls return explicit error. In the watch query, RAX contains nanoseconds and RDX informs how many timer interruptions have been met in the user. The test waits for the deadline and for at least two calls, including when the host delays a pulse. Return uses IRETQ after validating RIP/RSP and filtering user flags. SYSRET and compatibility with Windows syscal numbers remain outside of this delivery.

The preserved state includes general loggers, x87, SSE and MXCSR. The input code initiates x87/MXCSR, saved/restores context with FXSAVE64/FXRSTOR64 and keeps the direction of memory operations under control. The test checks the non-volatile loggers, XMM6, result x87 and DF through system call; XMM6/x87 also cross the period of user interruptions. AVX/XSAVE are not enabled on this initial platform.

## Destination of exceptions

CPU exceptions are not intercepted for host emulation in this mode: the output bitmap of the partition exception is zero. Guest stubs save context, call the dispatcher C++ and return by CPU. #UD and #PF known kernel autotest resume in explicit points. An unexpected kernel default records context and closes with observable failure.

The user test exercises #UD, CLI without privilege, kernel page reading, stack guard page, OUT attempt and INT attempt on kernel unique gateway. Register vector, CPL, RIP, RSP, RFLAGS, CR2 and error code. The failed user execution terminates and returns control to kernel routine. A new user input works then. Non-canon RSP on a syscall is refused before return; the record uses the `0x100` validation event.

Two unique images of the tests induce an unexpected kernel #UD and a double failure caused by invalid stack during the exception delivery. Double failure uses dedicated IST and sends report instead of disappearing into a silent reset. They are images generated by the project, not external files.

## Timer and watch

The paravirtual device uses the `0xEC` port, `0x40` vector and requested period of 5 ms. The host measures monotonic time since the start of this VM execution and publishes a read-only page for the guest. Each publication has version, boot ID and sequence. The guest validates format and monotonicity.

A host thread requests service outputs with WHvCancelRunVirtualProcessor. With vCPU stopped, the VMM updates the clock and asks for the interruption to be delivered. If IF is clean or there is interrupt shadow, requests interruption window notification and waits for the CPU to allow the delivery. Only then sets up the pending event. Do not overwrite another event. The actual guest RTD handler increases the counters and confirms the device service.

This cancellation of service resumes execution; the cancellation of watchdog continues terminal and has priority. Deactivation of the timer removes notifications and its pending event. Tests check clock progressing with disabled IF, absence of handlers in that window, service after STI, CPL0 and CPL3 interruptions, progress in user and deadline only after the time requested. Removing the pulse generator in the test results in explicit watchdog timeout.

The 5 ms period is nominal. Host scheduling can delay and combine salaries; there is no real-time guarantee. The clock has publishing resolution and can repeat the same value between updates. At this stage the test waiting uses PAUSE; there is no scheduler, wait for thread or support for idle/HLT with wakeup per timer. APIC/PIC/PIT are not emulated by this device.

## Layout and border

The basic boot 1.0 contract remains intact. In this mode, RDX points to the CPU extension versioned in `0x105000`; RCX continues pointing to BootInfo in `0x100000`. The extension describes clock, report, port, vector and period.

| GPA | Use and protection |
|---|---|
| `0x105000` | CPU Boot Extension, R |
| `0x106000` | Paravirtual Clock, R for guest |
| `0x107000` | Numerical report versioned, RW supervisor |
| `0x600000` | User's own code, RX after copying and sealing |
| `0x610000` | Front page of user stack, not present |
| `0x611000 .. 0x61FFFF` | User stack left, RW/NX |
| `0x620000` | User Data, RW/NX |

The `0x600000 .. 0x7FFFFF` range is reserved on the boot map. The guest installs an initial static map with user pages only for code, stack and defined data. Kernel pages are supervisor. User code goes from RW/NX to RX in the WHP before execution; it does not receive simultaneous write and execution permission. The extension and clock have write protection in the WHP.

There is still no allocation of pages, address spaces per process or migration from the manager MiniNt to the guest. This work continues in phase 3. The pagination structures of this phase are the minimum for the border CPL0/CPL3.

The CPU report has its own format, fixed size and maximum 12 default records. Report confirmation uses the CPU port; Hello, diagnostic and StopResult remain in the basic channel. Host validates format, version, session, reserved fields, limits and results before reporting success.

The loader maintains the refusal of files with data after sections. As the MSVC linker produces zeroed slash with these objects aligned, the build canonically only fills from zero in multiples of 512 bytes, limited to 4096 bytes. This step occurs on the compiled output before auditing. It is not applied to images received by the execution tool. There are trailer refusal tests with invalid content, excessive size or alignment.

## Limits and Stop

The demonstrated user execution is an assembly program created by the project, copied to a controlled page. It is neither a Windows application loader nor a process manager. The kernel continues with a vCPU, static map, fixed-size stacks and no thread preemption. Drivers, files, registry, NT/Win32 APIs and WinUI 3 interface remain in the corresponding phases. There is no physical boot by UEFI/BIOS in this delivery.
